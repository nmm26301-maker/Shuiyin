# 0.6.8 validation — 2026-10-23

- All production Java sources type-checked against Android 35 and the pinned engine dependencies with JDK 17. APK packaging is checked separately by the GitHub Android workflow.
- New checks: 15 concurrent search checks, 19 Douyin/photo checks, 21 executions of the actual automatic website script. This covers simultaneous launch, deduplication, signed URLs, preserving the original download contract, independent native-component failure, cancellation/timeout cleanup, real current provider response shapes, and XHS original-photo selection/fallback metadata and repair suggestions.
- Existing LinkTests, EngineTests, XhsTests, TransferTests, SaveWorkflowTests, MultiRegionTests, CatalogTests, GalleryQueueTests, DownloadSiteTests, gallery Python tests, platform catalog matching, FFmpeg repaired-media checks and both prior JS checks completed successfully. TransferTests initially reported a measured-bytes assertion failure; an isolated rerun passed and an independent real yt-dlp file transfer emitted the exact source byte count and total (12,742). The progress check should continue to be monitored.
- Website form selectors and result structures were checked against the currently served Cobalt HTML, TikTokio index.js, and GreenVideo index / video-store JS. The collector calls the site's own form, reads only complete media outputs, and does not synthesize API URLs or authentication tokens. GreenVideo's current site explicitly refuses Douyin links; this failure must not be described as that provider's Douyin support.
- Live public Douyin samples (upstream yt-dlp test URL and one current public indexed video) returned HTTP 200 mobile shells without the requested item data from this environment. The new SSR parser correctly rejected them; **no successful live Douyin download is claimed**. The original engine fallback remains. Region/login/site policy remains an unresolved limitation.
- No Android device/emulator was connected. Automatic form submission in Android WebView, actual three-site extraction, MediaStore saving, XHS original CDN availability and the visual result on the user's photos remain unverified. The new script tests use deterministic site-shaped fixtures and cannot replace those device checks.
- XHS photo repair still asks for confirmation of the suggested/remembered region and uses the existing pixel-fill implementation. A clean original should be saved by skipping repair. Complex backgrounds may show blur; no generative restoration or automatic watermark recognition is claimed.
